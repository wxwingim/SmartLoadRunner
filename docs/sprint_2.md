# Sprint 2 — Техническое задание

## 1. Сведения о спринте

**Тема спринта.** Функциональное ядро продукта: реальный исполнительный движок нагрузки в runner, управление жизненным циклом запусков, формирование итоговых отчётов и экспорт, минимальный веб-интерфейс (live-dashboard) и конвейер непрерывной интеграции (CI).

**Цель спринта.** Реализовать сквозной сценарий «YAML-сценарий → реальный запуск → потоковые метрики в веб-интерфейсе → итоговый отчёт и проверка SLA в CI». Исполнительный движок нагрузки выводит симулятор метрик из критического пути: нагрузка формируется реальными HTTP-запросами к целевой системе.

**Параметры выполнения.**
- Состав команды: 3–4 разработчика.
- Длительность: 2 недели (14 календарных дней).
- Оценка трудоёмкости: 60–70 единиц трудоёмкости (story points).

**Структура документа.** Работы декомпозированы на эпики (разделы 4.1–4.8) и детерминированные задачи с кодом (например, Э1-1). Задачи Эпика 1, реализованные в коде на момент составления документа, отмечены статусом «Реализовано»; прочие задачи — «Запланировано». Для каждой задачи указана конкретика: файлы, методы HTTP, имена хендлеров, выполняемые изменения и критерии приёмки.

## 2. Исходное состояние (итог Sprint 1)

Реализовано в Sprint 1:

- HTTP API координатора:
  - `POST /api/tests` — создание теста (тело — YAML-сценарий);
  - `POST /api/tests/{id}/run` — создание и запуск прогона (возврат `run_id`);
  - `POST /api/runs/{id}/metrics` — приём метрик от агента;
  - `GET /api/runs/{id}/stream` — поток событий (SSE) с метриками;
  - `GET /healthz` — проверка работоспособности.
- Хранилище данных: in-memory с моделью подписки (pub/sub); файловая персистенция `data/tests/<id>.yaml`, `data/runs/<id>.json` (метаданные), `data/runs/<id>.jsonl` (сырые метрики).
- Парсер YAML-сценариев и валидация (пакет `internal/scenario`).
- Конфигурация через переменные окружения `SLR_*`, файл `Taskfile.yaml`, `Dockerfile`, `docker-compose` (PostgreSQL/Redis — задел).
- Инструменты качества: golangci-lint, gofumpt, gci.

Ограничения Sprint 1, которые закрываются в Sprint 2:

- runner — эмулятор: генерирует синтетические метрики (пакет `internal/simulator`), реальные запросы к целевой системе не выполняет;
- запуски сразу получают статус `RUNNING` и не завершаются (отсутствует конечный автомат состояний);
- отсутствуют: суммаризация/отчёт, экспорт, гистограммы латентности, веб-интерфейс, CI;
- отсутствуют агентские эндпоинты координатора (регистрация агента, получение конфигурации запуска).

## 4. Декомпозиция на эпики и задачи

### 4.1 Эпик 1. Исполнительный движок нагрузки — реализован

**Э1-1. Создать пакет `internal/engine` — Реализовано.**

Состав пакета:

- `engine.go` — функция `Run(ctx context.Context, opts Options) error`:
  - создаёт `opts.VUs` горутин-воркеров;
  - тикер с периодом `opts.Interval` (по умолчанию 1 с) снимает снимок агрегатора и передаёт его в `opts.Sink`;
  - завершение работы по отмене `ctx` (сигналы ОС, таймер длительности, stop/abort из Эпика 2);
  - структура `Options`: `RunID`, `Scenario`, `VUs`, `Rate`, `Seed`, `Timeout`, `Interval`, `Sink`.
- `worker.go` — `vuWorker`:
  - последовательное выполнение шагов сценария (method, url, headers, body, think_time) реальными HTTP-запросами через `http.Client{Timeout: opts.Timeout}`;
  - успехом запроса считается HTTP-статус-код < 400, иначе фиксируется ошибка;
  - прекращение работы по отмене контекста между шагами и между итерациями.
- `aggregator.go` — `Aggregator`:
  - потокобезопасное накопление за отчётное окно: количество запросов, число ошибок, гистограмма латентности;
  - фиксированные бакеты гистограммы (логарифмическая шкала, 18 границ: 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1000, 2000, 4000, 8000, 16000, 32000, 64000, 128000 мс);
  - перцентили p50/p90/p99 оцениваются как середина бакета (без сортировки сырых значений);
  - снимок `snapshot(elapsed, activeVUs)` формирует `models.MetricBucket` и сбрасывает окно.
  - Примечание о фактическом поведении: RPS в снимке вычисляется как число запросов за окно, делённое на суммарное время с момента начала запуска; вопрос приведения расчёта к отчётному окну зафиксирован в задаче Э1-11.
- `ratelimit.go` — токеновый ограничитель `rateLimiter`: ёмкость и скорость пополнения равны заданному количеству запросов в секунду.
- `coordinator.go` — клиент `CoordinatorClient`:
  - `RegisterAgent(ctx, Agent) (agentID string, err error)` → `POST /api/agents`;
  - `GetRunConfig(ctx, runID) (*RunConfig, error)` → `GET /api/runs/{id}/config` (парсинг и валидация сценария на стороне агента);
  - `ReportMetrics(ctx, *MetricBucket) error` → `POST /api/runs/{id}/metrics`.

### 4.3 Эпик 2. Управление жизненным циклом запусков (координатор)

Все задачи эпика — **Запланировано**.

**Э2-1. Реализовать сервисный слой `RunManager` — пакет `internal/service`.**

- создать файл `internal/service/runmanager.go`; структура `RunManager` с зависимостью от `store.Storage`;
- методы сервиса: `CreateRun`, `MarkRunning`, `StopRun`, `AbortRun`, `FinalizeRun`, `WatchdogTick`;
- подключить `RunManager` к хендлерам через поле `httpapi.Handlers.RunManager`.

**Э2-2. Реализовать конечный автомат состояний запуска.**

- последовательность состояний: `SCHEDULED → STARTING → RUNNING → (STOPPING) → COMPLETED | FAILED | ABORTED`;
- правила переходов:
  - создание запуска → `SCHEDULED`;
  - сигнал от агента (регистрация или первая метрика) → `RUNNING`;
  - stop → `STOPPING`, по истечении grace-периода → `COMPLETED`;
  - abort → `ABORTED` (немедленно);
  - истечение сторожевого таймаута без метрик → `FAILED` (с диагностическим сообщением в записи запуска);
- использовать существующие константы `models.State*` в `internal/models/model.go`;
- приёмка: юнит-тесты допустимых и недопустимых переходов, идемпотентность stop/abort.

**Э2-3. Изменить хендлер `StartRun` (`POST /api/tests/{id}/run`).**

- текущее поведение: запуск создаётся сразу со статусом `RUNNING` (см. `httpapi/handlers.go`, поле `Status: models.StateRunning`);
- целевое поведение: создать запуск со статусом `SCHEDULED`, сохранить через `Store.SaveRun` и персистенцию, вернуть `run_id`; переход в `RUNNING` — по факту получения метрик от агента (конфигурация агент уже получает через `GET /api/runs/{id}/config`);
- приёмка: новый запуск наблюдается в статусе `SCHEDULED` через `GET /api/runs/{id}`.

**Э2-4. Добавить хендлер `GetRun` — `GET /api/runs/{id}`.**

- возврат полной записи `models.Run` (включая `status`, `metrics_summary`); `404` при отсутствии запуска;
- зарегистрировать маршрут в `httpapi/router.go`.

**Э2-5. Добавить хендлер `ListRuns` — `GET /api/runs`.**

- возврат списка запусков, сортировка по дате создания (новые выше); минимальная поддержка `limit` и `offset` через query-параметры;
- зарегистрировать маршрут в `httpapi/router.go`.

**Э2-6. Добавить хендлер `StopRun` — `POST /api/runs/{id}/stop`.**

- переход в `STOPPING`: ожидание grace-периода, затем `COMPLETED`; повторные вызовы — идемпотентны;
- зарегистрировать маршрут в `httpapi/router.go`.

**Э2-7. Добавить хендлер `AbortRun` — `POST /api/runs/{id}/abort`.**

- немедленный переход в `ABORTED` с отменой контекста движка; повторные вызовы — идемпотентны;
- зарегистрировать маршрут в `httpapi/router.go`.

**Э2-8. Финализация запуска.**

- при переходе в `COMPLETED`, `FAILED` или `ABORTED` сохранить снапшот сценария и итоговую сводку в `Run.MetricsSummary`;
- записать обновлённую запись через `Persistence.SaveRun` (`internal/store/file_store.go`);
- при старте координатора восстанавливать статусы запусков из диска (`Persistence.LoadAll`).

**Э2-9. Расширить `internal/store`.**
- интерфейс `Storage` дополняется методами `UpdateRun(ctx, *models.Run) error` (обновление статуса и summary) и `ListRuns(ctx) ([]*models.Run, error)`, если они не введены ранее.

**Э2-10. Критерий приёмки Эпика 2.**

- при штатной работе запуск завершается в `COMPLETED`; при недоступности агента — в `FAILED`;
- stop соблюдает grace-период; abort выполняется мгновенно;
- `GET /api/runs/{id}` отражает текущее состояние на всех этапах.

## 6. Ключевые технические решения

- Использование стандартной библиотеки (`net/http`, SSE); новые тяжёлые внешние зависимости в Sprint 2 не добавляются.
- Гистограмма латентности: фиксированные логарифмические бакеты (18 границ от 1 мс до 128 с); агрегация на координаторе; перцентили оцениваются по бакетам без хранения и сортировки сырых значений.
- Регистрация агентов без криптографического подтверждения (до Sprint 3); распределение нагрузки выполняется координатором с учётом capacity агентов.
- Распределение конфигурации запусков: модель pull — агент забирает конфигурацию через `GET /api/runs/{id}/config`; схема совместима с будущим переходом на gRPC.
- Конфигурация приложения: расширение существующей схемы `SLR_*`, новый механизм конфигурирования не вводится.

## 7. Критерии готовности (Definition of Done)

- `task format`, `task lint`, `task test` проходят успешно (тесты — с `-race`).
- Сквозной сценарий: создать сценарий → запустить прогон → увидеть живые метрики в веб-интерфейсе → прогон завершается в `COMPLETED` → отчёт и экспорт согласуются с фактическими агрегатами.
- Работа `load-test` в CI завершается успешно при соблюдении SLA и неуспешно при его нарушении.
- Документация Sprint 2 соответствует фактическому состоянию системы.
